## 1. 项目定义

**Aki Music** 是一款桌面音乐播放器（Electron 三平台），定位为「**YesPlayMusic 的完整功能 + Folia 级别的全屏歌词体验**」。

### 产品目标（按优先级）

| 优先级 | 目标 | 验收信号 |
|---|---|---|
| P0 | 保留 YesPlayMusic 全部既有能力，功能不倒退 | 0.4.11 的所有页面/操作在新架构下可用 |
| P0 | **逐字歌词**：字级高亮、翻译、罗马音、背景人声 | 任意有 TTML/yrc 的歌曲逐字跟随，误差 < 200ms |
| P0 | **全屏歌词视觉**达到 Folia 观感 | 至少 3 种视觉模式 + 模糊/动态背景，60fps |
| P1 | **双人「一起听」** | 两台设备同步播放/进度/歌单 |
| P1 | 稳定的音源与接口 | 灰色歌曲可播，接口随 api-enhanced 更新 |
| P2 | 打包发布 | Windows / macOS / Linux 安装包 |

### 技术目标

- 消除历史包袱：Node 14/16 → 22 LTS；Webpack 4 → Vite；Electron 13 → 30+；渲染进程安全模型重建
- 新代码全部 TypeScript；歌词引擎与可视化层**框架无关**，可独立测试与复用
- 建立回归保护：核心逻辑单测 + UI 冒烟测试

## 2. 关键决策记录

### D1：基线选择 —— YesPlayMusic 作为功能骨架 ✅

用 YesPlayMusic 承载 UI、路由、状态、播放器、平台集成（托盘/MPRIS/TouchBar/快捷键/Discord/Last.fm/音源降级链），Folia 只贡献**歌词与视觉**。

**理由**：YesPlayMusic 的分层清晰、功能已验证、改动半径可控；Folia 有 1,642 个 TS 文件与一个 137 KB 的 `App.tsx`，整体接管的学习成本远高于移植歌词层的成本。

### D2：许可证 —— 全库 AGPL-3.0 ✅

接受 AGPL 后，**Folia 的源码从"只能看"变成"可以直接移植"**，这是本计划最大的成本节约项：歌词解析、字素计时、CJK 语义布局、字级着色/发光等模块（合计数千行、技术门槛最高的部分）无需重写。

代价与义务见[第 8 章](#8-agpl-合规方案)，**必须在本项目写第一行代码前落地**。

### D3：框架 —— Vue 2.7 过渡，Vue 3 后置

| 方案 | 迁移成本 | 说明 |
|---|---|---|
| **Vue 2.7 + Vite（选定）** | 低（近乎零改动） | 2.7 是 Vue 2 终版，内置 Composition API，可由 `@vitejs/plugin-vue2` 接入 Vite。19 个页面 + 22 个组件**无需改写** |
| Vue 3 一步到位 | 中高（41 个文件 / ~12K 行 Vue，机制性改写） | 收益是长期可持续，但会推迟歌词（核心差异化）数周 |
| 保持 Vue 2.6 + Webpack 4 | 零 | 无法使用 TS 生态与现代依赖，`esbuild-loader` 补丁继续存在 ❌ |

**决策**：M1 升级到 **Vue 2.7 + Vite + TS**，把框架迁移推迟到 M6（歌词完成后）。理由：

1. Vue 2 EOL 的风险主要是"安全补丁 + 生态"，而本应用（a) 渲染进程在 M1 完成 `contextBridge` 沙箱化改造，（b) 不引入新的 Vue 生态库，风险可控；
2. 迁移虽机制化但涉及 41 个文件，收益不对用户可见，**优先级低于歌词**；
3. 2.7 的 Composition API 让新代码按 Vue 3 风格书写，未来迁移可近乎复制；
4. 歌词引擎自始即框架无关，**不受后续框架迁移影响**——这是把它设计成独立模块的核心动机。

### D4：歌词数据源 —— 三级优先 + 本地缓存

**不需要自建镜像、不需要爬取**。已核实：

| 级别 | 来源 | 能力 | 覆盖 |
|---|---|---|---|
| ① 首选 | **AMLL 官方 API** `api.amll.dev/v1/lyrics/get?ncmMusicId=` | 人工校对 TTML：逐字 + 翻译 + 罗马音 + 背景人声 | 网易云 3,587 首（ncm 库） |
| ② 回退 | **网易云 `/api/song/lyric/v1`**（`api-enhanced` 的 `lyric_new`） | 机器逐字 `yrc` + 翻译 `ytlrc` + 罗马音 `yromalrc` | 覆盖极广 |
| ③ 兜底 | 网易云 `/lyric`（行级 LRC） | 行级 + 翻译 + 罗马音 | 几乎全覆盖 |

关键约束：AMLL 官方 API **单 IP 平均限流约 50 次/秒**，Electron 侧应带上可识别 UA 并串行化请求；结果落地 Dexie 缓存（复用 YesPlayMusic 已有的 `lyric` 表）。

### D5：双人房优先，多人房不做 ✅

`api-enhanced` **已内置 9 个双人房模块**（`listentogether_room_create` / `room_check` / `accept` / `end` / `status` / `heatbeat` / `play_command` / `sync_playlist_get` / `sync_list_command`），开箱可用。

多人房所需的 5 个 `listentogether_multi_match_*` 模块**在 `@neteaseapireborn/api` 与 `api-enhanced` 中均不存在**——执行 D5 后，这个已知阻塞点直接消失。

### D6：音频频谱 —— 改走本地代理

要做频谱可视化，必须用 Web Audio 的 `AnalyserNode`；而当前 Howler 配置为 `html5: true`（纯 `<audio>` 元素），且音源跨域。

**这是一个必须提前规避的陷阱**：对跨域 `<audio>` 调用 `createMediaElementSource()` 且该资源未获 CORS 批准时，音频会变哑（输出静音）。网易云 CDN 与 UnblockNeteaseMusic 各音源都不保证返回 CORS 头。

**方案**：在已有的本地 express 服务（`127.0.0.1:27232`）上新增 `/audio-proxy`，**透传 Range 请求**（seek 必需）+ 域名白名单，音频改为同源播放后再建图。（已缓存歌曲走 IndexedDB blob URL，天然同源，无此问题。）

### D7：保留现有歌词背景 + 统一风格系统与开关 ✅

**要求**：**不得丢弃** YesPlayMusic 现有的 4 种歌词背景（关闭 / 渐变 / 封面模糊 / 动态封面），并新增一个可在设置页与歌词页内**即时切换**的风格开关。

**做法**：不维护两套并行代码，而是把现有 4 种背景重构为新风格框架的**首批内置模式**，与 Folia 派生的可视化模式共享同一契约（`id` / `cost` / `mount` / `update` / `destroy`）。老设置值经 `updateApp.js` 一次性迁移，配置不丢。

**理由**：

1. 避免"旧背景 + 新背景"两套渲染路径各自演化；
2. 统一契约后，**成本标注、自动降级、资源回收只需实现一次**；
3. 歌词页是**常驻组件**（`App.vue` 中 `v-show` 而非 `v-if`），只有统一生命周期管理才能防止切换时显存泄漏。

**排期影响**：现有背景的移植与开关**必须落在 M2**（因为 M2 会重写歌词页，否则相对 0.4.11 出现功能回归），M3 只负责**新增**模式。

### D8：网络层 —— 以「消除冗余」换速度，而非「提高并发」✅

**判断**：本应用**瓶颈不在本地链路**（本地两个服务之间是 localhost 回环，单跳 < 1ms），而在**出站请求的数量与重复度**。盲目提高并发数会触发网易云风控与 AMLL 限流（官方约 50 次/秒/IP），**结果更慢**。

**策略**（按投入产出比排序，详见[第 6 章](#6-网络层与请求性能高并发与响应速度)）：

1. **消除重复请求** —— 已定位到确定性缺陷：`getTrackDetail` / `getLyric` 在缓存未命中时会**并发发出两次完全相同的请求**；补全全局 in-flight 去重与 `AbortController` 取消
2. **新增内存 LRU 缓存层** —— 把高频对象（当前曲目/歌词/歌单）的命中从"异步读 Dexie"降到微秒级
3. **喂好服务端 2 分钟缓存** —— api-enhanced 已内置按 URL 的 2 分钟响应缓存；只读接口**禁止注入时间戳等易变参数**，否则缓存永不命中
4. **优先级调度 + 批量合并** —— P0 播放路径永不被后台任务阻塞；散落的单曲请求聚合成批量请求
5. **预取并行化** —— 下一首的音源 / 歌词 / 封面 / 详情改为并行预取（当前是串行链）

**明确不做**：不对多个解锁音源并发竞速（放大风控风险）；不追求最大并发数。

### D9：背景「随歌曲情感/风格变幻」—— 离线封面取色，不接 LLM ✅

调查发现 folia 的「情感变幻」有两条路径：① **离线**：从封面提取主色/辅助色，按和声方案
（analogous/complementary/split/triadic/duotone/monochrome）生成亮/暗双主题，并用 WCAG
对比度下限保证可读性；② **AI**：把歌词喂给 LLM，返回主题色 + 关键歌词的逐词配色。

**决策：只做 ①**。理由：完全离线、零 API key、每首歌自动不同；且 folia 自己也把它作为
AI 失败时的回落路径。代价：配色由封面决定，「情感」是间接的（封面风格 ≈ 歌曲风格），
且没有逐词配色 —— 逐词高亮仍由 D7 的字级着色实现。

### D10：桌面歌词 —— **要壁纸层（歌词在桌面图标之下），先只支持 Windows** ✅

folia 里「桌面歌词模式」其实是**主窗口的一组开关**（透明 + 置顶 + 不占任务栏 + 点击穿透），
而「壁纸层」（歌词沉到桌面图标之下）是另一套需要三平台原生代码的功能。

**决策：做壁纸层，但先只做 Windows**（用户所在平台即 Windows 11，folia 注释指出
透明窗口仅在 Win11 24H2+ 的「raised」桌面下能存活于 SetParent 之后，本机符合）。

**不写 Rust**：folia 用 Rust 助手（`folia-wallpaper-helper.exe`）做 WorkerW 注入，
但它自己在 macOS 侧用的 **koffi FFI 同样能调用 Windows API**（FindWindow/EnumWindows/
SendMessageTimeout/SetParent）→ 可以在 Electron 主进程里用纯 JS 实现，避免引入
额外的 Rust 构建链路。folia 明确警告的两点必须照做：
- **鼠标转发是硬契约**：壁纸层窗口收不到真实点击，需注入输入（Raw Input → `sendInputEvent`）
- 壁纸模式下**点击穿透无意义**（窗口在图标层之下，真实点击根本到不了它）—— folia 直接拒绝该组合

### D11：字体策略 —— 现有打包字体 + 系统字体栈 + 允许上传 ✅

- **预设**：项目已打包 Barlow（5 个字重）；再移植 folia 的系统字体栈
  （Inter / Noto Sans CJK / PingFang / 微软雅黑 等，按平台回落）
- **本机字体**：用 **Local Font Access API**（`window.queryLocalFonts()`，Chromium 专有，
  Electron 可用）列出本机字体供选择 —— folia 的字体选择器正是这么做的
- **自定义上传**：移植 folia 的上传链路（校验 woff2/ttf ≤ 50MB → 存本地 → `FontFace` 注册）
- **不额外打包 CJK 字体**：会显著增大安装包，且需逐一核验字体许可证

### D12：音频频谱反应移出本轮 ✅

folia 确实有音频图（`services/playbackGraph.ts` 的
`decks → mix → equaliser → effects → volume → fade → analyser → out`，
`usePlaybackAudioBridge.ts` 设 `fftSize = 2048`），但**本轮要移植的 6 项功能都不依赖它**：
- 「歌词在桌面跳动」在 folia 里是**呼吸浮动动画**（行的 y/scale 循环），非音频驱动
- 背景的音频反应只驱动**运动速度**，不驱动色相（色相来自封面或 AI 主题）

**决策：本轮不做**，从而避开改造播放链路的风险（跨域音频建 Web Audio 图会变哑）。
音频图 + `/audio-proxy` 随「视觉深化」一并评估。

```
│  ├─ 原生音源解锁：@unblockneteasemusic/rust-napi                       │
│  └─ 歌词：Dexie 缓存 + AMLL API 拉取（主进程代理，带可识别 UA）          │
└────────────────────────────────────────────────────────────────────────┘
                                   │ HTTPS
                    ┌──────────────┴──────────────┐
                    │ api.amll.dev（逐字 TTML）    │
                    │ 网易云官方接口（yrc / lrc）   │
                    └─────────────────────────────┘
```

**架构原则**：

1. **歌词引擎与可视化层零框架依赖**——纯 TS 模块，输入 `LyricData` + 时间 + 频谱，输出渲染结果。这使得（a) 可独立单测，（b) 未来 Vue 2→3 迁移不受影响，（c) 可视化模式可被独立替换。
2. **音频必须同源**——缓存 blob 或本地代理，二者选一，绝不直接对跨域流建 Web Audio 图。
3. **接口白名单不变**——继续用 `ncmModDef` 式的显式声明，替换依赖时不改变架构。

## 5. 核心模块设计

### 5.1 歌词引擎（核心）

**分层设计**（`src/lyrics/`，纯 TS，无 Vue/React 依赖）：

```
┌──────────────────────────────────────────────────────────┐
│ 1. sources/  数据获取与调度                                │
│    amllDb.ts      AMLL 官方 API（主进程代理，串行+UA）      │
│    neteaseYrc.ts  /lyric/new → yrc 逐字                    │
│    neteaseLrc.ts  /lyric → lrc + tlyric + romalrc          │
│    index.ts       优先级调度 · 超时降级 · Dexie 缓存        │
│    ↳ 统一产出：{ format, raw, source, quality }             │
├──────────────────────────────────────────────────────────┤
│ 2. core/  解析与规范化                                     │
│    parserCore.ts   格式探测 + 分派（移植自 folia）           │
│    adapters/       ttml · lrc · elrc · yrc · qrc · krc · vtt│
│    types.ts        LyricData / Line / Word（稳定数据契约）   │
│    ↳ 统一产出：{ lines: [{ words:[{text,start,end}],        │
│                    translation, roman, bg }] }             │
├──────────────────────────────────────────────────────────┤
│ 3. timing/  时间轴细化（移植自 folia）                      │
│    graphemeTiming.ts     字素级计时（Intl.Segmenter）        │
│    cjkSemanticLayout.ts  CJK 语义分组、标点吸附              │
│    renderHints.ts        逐字揭示曲线（word reveal profiles）│
├──────────────────────────────────────────────────────────┤
│ 4. render/  纯函数渲染计算（移植自 folia，可直接复用）       │
│    wordColoring.ts  当前时刻的字级高亮区间                   │
│    wordGlow.ts      发光区间与强度                          │
│    ↳ 输出：高亮/发光范围，交给渲染层绘制                     │
└──────────────────────────────────────────────────────────┘
```

**关键设计点**：

- **稳定的中间契约**：`LyricData`（行 → 词 → 可选音节）是整个系统的唯一数据形状，所有格式适配器都归一到它。这样才能做到「换数据源不影响播放页，换渲染层不影响解析」。
- **质量分级**：`source` 与 `quality` 字段随 `LyricData` 一起传递，UI 可显示歌词来源（如「AMLL 校对」/「网易云逐字」/「普通歌词」），也便于问题定位。
- **失败必须降级而非报错**：AMLL 超时（5s）→ yrc → lrc；全失败则显示「暂无歌词」并保留纯音乐视觉。
- **缓存策略**：沿用现有 Dexie `lyric` 表，键为 `trackId`，同时记录 `source` 与 `updateTime`；命中即用，不重复请求。缓存容量与淘汰复用现有 `deleteExcessCache` 机制。

### 5.2 音频频谱桥（含一个必须提前规避的陷阱）

**目标**：为可视化提供实时的分带能量（0..255），并做平滑。

**实现路径**：

```
Howler(<audio>) ──► MediaElementSource ──► AnalyserNode ──► 分带能量 ──► 平滑 ──► 可视化
                                            (fftSize 2048)    (0..255)
```

**三个必须处理的问题**：

1. **跨域静音陷阱（最高优先）**：对未获 CORS 批准的跨域音频调用 `createMediaElementSource()` 会导致**输出静音**。
   - 解决：统一走同源 —（a）已缓存歌曲用 IndexedDB blob URL（天然同源，无成本）；(b) 未缓存歌曲经新增的 **`/audio-proxy`**。
   - 也可选择「先缓存再播放」策略，让大部分播放走 blob 路径，代理仅作兜底。

2. **`/audio-proxy` 必须支持 Range**：音频 seek 依赖 HTTP Range 请求，代理需原样透传 `Range` / `Content-Range` / `Accept-Ranges` / `Content-Length`，并保持流式（不可整体读入内存）。
   - 域名白名单：`*.music.126.net`、`*.bilivideo.com`、UNM 各音源域名；拒绝非白名单目标，避免被当作开放代理。
   - 顺带收益：统一同源后，`setSinkId`（输出设备切换）与缓存逻辑的可靠性都会提升。

3. **与 Howler 的耦合**：需要访问底层 `<audio>` 节点（当前代码已在 `setOutputDevice()` 里访问 `_howler._sounds[0]._node`）。**建议在 M1 封装一个 `PlaybackGraph` 服务**隔离对 Howler 私有字段的直接依赖，把「取节点、建图、接分析器、取分带」集中在一处，避免散落各处（这也是技术栈分析中标记的开发债 #9）。

### 5.3 全屏歌词视觉层（含背景风格系统）

**目标**：达到 Folia 的观感，但**不引入 React**；同时**完整保留 YesPlayMusic 现有的 4 种歌词背景**，并新增统一切换入口。

#### 5.3.1 现有背景：必须原样保留，不得回归

当前实现（`src/views/lyrics.vue` + `src/views/settings.vue`）已有 4 种背景，**全部保留**：

| 现有设置值 | 呈现 | 实现 | 成本 |
|---|---|---|---|
| `false`（关闭） | 无背景 | 纯 `--color-body-bg` | 无 |
| `true`（打开） | 纯 CSS 渐变 | `.gradient-background`，`background` 由封面主色（`node-vibrant`）推导 | 极低 |
| `'blur'`（模糊） | 封面图模糊铺底 | `.lyrics-background` 两处定位（top-right / bottom-left）+ `--contrast-lyrics-background` / `--brightness-lyrics-background` 变量控制 | 低 |
| `'dynamic'`（动态） | 封面图动态背景 | `.dynamic-background` | 中（i18n 已标注「GPU 占用较高」） |

> 现有 i18n 文案已为 `dynamic` 标注了 GPU 成本，说明「按成本提示用户」是既有产品语言的一部分，新风格系统应延续这一做法。

#### 5.3.2 统一风格系统：把现有背景变成"首批内置模式"

**关键设计决策**：不保留两套并行代码，而是把现有 4 种背景**重构为新风格框架的首批实现**，与 Folia 派生的新模式**同构**。

```
src/visualizers/
├─ registry.ts              # 自注册（import.meta.glob）
├─ types.ts                 # VisualizerDefinition 契约
├─ backdrops/               # 背景系统
└─ modes/
   ├─ off/                  # ← 现有 false
   ├─ gradient/             # ← 现有 true（CSS 渐变 + node-vibrant 取色）
   ├─ blur/                 # ← 现有 'blur'（封面模糊）
   ├─ dynamic/              # ← 现有 'dynamic'（动态封面）
   ├─ still/                # ★ 新增：静态暗场（成本最低、护眼）
   └─ <gpu-mode…>/          # ★ 新增：移植自 Folia 的可视化模式
```

**契约 `VisualizerDefinition`** —— 每个模式声明：

| 字段 | 说明 |
|---|---|
| `id` | 稳定标识，用于设置持久化，**一旦发布不可改名** |
| `name` / `description` | 多语言展示名 |
| `cost` | `'none' \| 'low' \| 'medium' \| 'high'` —— 驱动 UI 成本标注与自动降级 |
| `mount(el, ctx)` | 挂载渲染器，返回句柄 |
| `update(frame)` | 每帧更新（当前时间、当前行/词、频谱分带、封面主色） |
| `destroy()` | **必须彻底释放 GPU 资源**（Pixi/three 的 dispose） |
| `capabilities` | 需要哪些输入（频谱 / 封面主色 / 时间轴）—— 无需求即不订阅，避免无谓计算 |

#### 5.3.3 开关：两个入口 + 平滑切换

| 入口 | 用途 | 位置 |
|---|---|---|
| **设置页** | 持久化选择，带成本标注 | `views/settings.vue`（复用现有 `lyricsBackground` 下拉位置） |
| **歌词页内快捷切换** | 不离开页面即时切换，便于对比风格 | 歌词页右键菜单（复用现有 `ContextMenu` 组件）+ 可选浮动按钮 |

**切换的工程要求**（易被低估，需明确验收）：

1. **不中断音频、不重载歌词数据** —— 只替换渲染层，`LyricData` 与播放状态原地保留。
2. **平滑过渡** —— 交叉淡入（约 300ms），避免黑屏闪烁。
3. **彻底回收资源** —— 歌词页是**常驻组件**（`App.vue` 中 `<Lyrics v-show="showLyrics" />`），反复切换若不销毁旧渲染器会**持续累积显存**。必须在 `destroy()` 中显式释放，并加一条「切换 50 次后显存不增长」的验收。
4. **成本保护**（延续现有 `dynamic` 的提示思路）：
   - 尊重 `prefers-reduced-motion`
   - 高成本模式监测帧率，持续低于阈值（如 < 40fps）时提示或自动降级到 `blur`
   - 提供「性能优先」总开关：一键把所有高成本模式降级
   - 可选：电池供电时默认降级（`navigator.getBattery`）

#### 5.3.4 设置项迁移（老用户配置不丢）

现有 `settings.lyricsBackground` 是**混合类型值**（`false | true | 'blur' | 'dynamic'`），需迁移为稳定的字符串 ID：

```
settings.lyricsBackgroundStyle: 'off' | 'gradient' | 'blur' | 'dynamic' | <modeId>
```

映射：`false → 'off'`、`true → 'gradient'`、`'blur' → 'blur'`、`'dynamic' → 'dynamic'`。

**必须用现有机制**：`src/utils/updateApp.js` 已在启动时按 `appVersion` 做 localStorage 迁移（由 `store/state.js` 调用），在此追加一次性迁移，并保留「读旧值兜底」，确保升级用户与全新用户都能正常工作。

#### 5.3.5 移植策略（Folia → Aki）

| 层 | Folia 的实现 | 我们的做法 |

### 5.6 桌面歌词与远程控制（Electron 层，对应 M3）

**两个决定移植方式的事实**（来自对 folia 的实测调查）：

1. 「桌面歌词模式」**不是独立窗口**，而是**主窗口的一组开关**：点击穿透 + 置顶 + 透明背景 + 不占任务栏
   （`electron/main.cjs` 的 `isDesktopLyricModeActive()`）
2. 「远程控制」**是第二个窗口**：450×230、透明无边框、置顶、不占任务栏，自带迷你播放器与歌词覆盖层

Windows 平台**官方 Win11 24H2+ 的「raised」桌面**才允许透明窗口存活于 `SetParent` 之后；
folia 在经典桌面下**拒绝**开启并提示，而不是静默失败 —— 我们照做。

**桌面歌词（壁纸层，Windows）**

| 环节 | folia 的做法（源文件） | 我们的做法 |
|---|---|---|
| 沉入图标层 | Rust 助手 `folia-wallpaper-helper.exe`：`SetParent` 到 WorkerW（`packaging/windows/wallpaper-helper/src/attach.rs`） | **用 koffi 在主进程实现**，不引入 Rust 构建链：EnumWindows 找 Progman → `SendMessageTimeout(0x052C)` 触发 WorkerW → `SetParent` |
| 输入转发 | Raw Input 只转发鼠标移动 + 左键 → `webContents.sendInputEvent`（`electron/windowsWallpaperMouse.cjs`） | 同思路（koffi 注册 Raw Input，或退化为光标轮询 + `sendInputEvent`）。**这是硬契约**：不转发则歌词不可交互 |
| 崩溃自愈 | 心跳 5s / 超时 15s 重挂 + 崩溃计数落盘 | 同思路：心跳 + 重挂 + 超限则自动退出壁纸模式 |
| 窗口参数 | `skipTaskbar` / `resizable:false` / `movable:false` / `backgroundColor:'#00000000'` | 沿用 |
| 点击穿透 | 壁纸模式下**被拒绝**（窗口在图标层之下，真实点击到不了它） | 同：该组合不提供，避免给用户一个"看似开启实则无效"的开关 |

**远程控制窗口**

| 环节 | folia 的做法 | 我们的做法 |
|---|---|---|
| 窗口 | `frame:false` + `transparent:true` + `hasShadow:false` + `alwaysOnTop`（level `screen-saver`）+ `skipTaskbar` | 同 |
| 右上角控件 | 光标进入顶部 44px 显示：调色板（背景模式循环）/ 固定 / 关闭 | 同（Vue 实现） |
| 播放控制 | 上一个 / 播放暂停 / 下一个 / 循环 / 喜欢 / 进度条；**空闲 800ms 后控制区被歌词覆盖层替换** | 同 |
| 透明控制面板 | 标准↔透明切换、UI 可见性循环、边框、**点击穿透**、置顶主窗口 | 同 |
| 同步 | 主窗口每 500ms 且变更时推快照（含**已解析的 LyricData**）→ 主进程缓存（500ms 心跳缺歌词字段时**保留上一次**）→ 推给远程窗口；远程**自己插值时钟**并用 rAF 直接改 DOM 渲染 | 同（我们的引擎已产出 LyricData，直接复用） |
| 通道 | 全 IPC（渲染 ↔ 主进程 ↔ 远程窗口）；folia 的 Stage API 是**独立的**本地 HTTP+WS 服务，与面板无关 | 同 |

**点击穿透必须有恢复路径**（folia 的三个细节必须照抄）：

1. `setIgnoreMouseEvents(enabled && !unlockHover, { forward: true })` —— `forward:true` 让
   `mousemove` 继续到达渲染进程，否则**无法解锁**（窗口会变成一块点不动的死区）
2. **解锁热区**：右上角矩形（84×40），两个探测器并行 —— 主进程每 150ms 轮询
   `screen.getCursorScreenPoint()`，渲染进程在 `mousemove` 里命中测试；任一命中即临时
   关闭穿透，使解锁按钮可点
3. **热区常量在两处重复**（主进程 + 渲染进程）且必须一致 —— 我们改为**单一常量模块**避免漂移

同时渲染进程要主动锁住指针事件：`html[data-click-through='active'] body * { pointer-events: none !important }`（例外类 `.click-through-interactive`），否则悬停样式会残留。

**一个必须一起做的工程点**：Electron 里「透明」是**建窗期标志**，切换会**重建窗口**，
播放因此会中断。folia 用播放交接解决（`electron/windowPlaybackHandoff.cjs` + 3 个 IPC
通道 + 15 秒 TTL + 落盘以跨重启）。原项目没有这层能力，**需要新写**。

## 6. 网络层与请求性能（高并发与响应速度）

> **先纠正一个直觉**：本应用的瓶颈**不在本地链路**。渲染进程到主进程的两个本地服务（`27232` / `10754`）是 localhost 回环，单跳 < 1ms，**优化这一跳的收益可以忽略不计**。真正的瓶颈是**出站请求到网易云 / AMLL 的延迟与请求数量**。因此优化方向是「**减少出站请求的数量与重复**」，而不是「提高并发数」。

### 6.1 先量化：建立性能基线（无度量不优化）

| 指标 | 采点 | 目标 |
|---|---|---|
| 冷启动到可交互 | 进程启动 → 首页渲染完成 | < 3s |
| 切歌到出声（音源缓存命中） | 点击 → `play` 事件 | < 150ms |
| 切歌到出声（无缓存） | 点击 → `play` 事件 | 不劣于现有基线 |
| 歌词首次显示 | 切歌 → 首行高亮 | 缓存 < 300ms / 远程 < 1.5s |
| 歌单页首屏（500 首） | 路由进入 → 首屏内容可见 | 1s 内可见项，图片渐进加载 |
| 搜索响应 | 输入 → 结果渲染 | 防抖 200ms 后 p95 < 600ms |
| **重复请求率** | 同一 URL 的冗余请求占比 | **目标 0** |

工具：Playwright trace（网络瀑布 + 主线程火焰图）+ 轻量请求埋点（记录 URL、耗时、是否命中缓存、是否重复）。

### 6.2 第一优先级：消除重复与无效请求（收益最大、成本最低）

**已定位到两处确定性缺陷**（`src/api/track.js`）：

```js
export function getTrackDetail(ids) {
  const fetchLatest = () => { /* request(...) */ };
  fetchLatest();                     // ① 无条件发起一次
  ...
  return getTrackDetailFromCache(idsInArray).then(result => {
    return result ?? fetchLatest();  // ② 缓存未命中时，又发起一次完全相同的请求
  });
}
```

`getLyric` 是同样的结构。**后果**：缓存未命中时，同一个 URL 会**并发发出两次**请求——服务端 2 分钟缓存虽能挡住第二次的出站流量，但仍支付两次本地往返与两次序列化。

**改造清单**：

| 措施 | 说明 |
|---|---|
| 正确化 SWR | 明确区分「读缓存」与「后台刷新」：缓存命中时**不阻塞渲染**、后台刷新**去重且可取消**；缓存未命中时**只发一次** |
| 全局 in-flight 去重 | 以「方法 + URL + 关键参数」为键维护 `Map<key, Promise>`，并发相同请求复用同一个 Promise |
| `AbortController` 取消 | 路由离开 / 新搜索 / 切歌时取消该上下文的在途请求，释放连接与主线程 |
| 请求键归一化 | 参数顺序、`ids` 排序、冗余参数统一，避免「同一语义、不同 URL」造成缓存穿透 |

> 这一项预计可消掉 **30%～50% 的冗余请求**，且不改动任何业务逻辑，是投入产出比最高的改动。

### 6.3 缓存分层：把「响应速度」从网络问题变成内存问题

```
① 内存 LRU（会话级，命中 < 1ms）        ← ★ 新增：高频对象
② Dexie / IndexedDB（持久，命中 < 10ms） ← 已有：trackDetail / lyric / album / trackSources
③ 服务端响应缓存（按 URL 2 分钟）        ← 已有：api-enhanced 内置
④ HTTP 缓存（Electron 自动）             ← 封面图等静态资源
⑤ 出站请求（真正花时间的那一层）
```

**要点**：

- **内存 LRU 是新增的关键层**。当前没有会话级缓存，每次都读 Dexie（异步 + 结构化克隆开销）。对「当前曲目、当前歌词、当前歌单」这类高频对象加内存层，可把命中从毫秒级降到微秒级。
- **服务端 2 分钟缓存要「喂好」**：api-enhanced 的 `util/apicache.js` 按请求 URL 缓存。**任何易变参数都会破坏缓存键**——现有代码在 `likeATrack` / `scrobble` 中注入 `params.timestamp = new Date().getTime()`（写操作，本就不该被缓存，无妨），但**只读接口必须禁止**注入时间戳/随机数，否则缓存永不命中。建议在请求层立一条硬规则并在 review 时检查。
- **缓存 TTL 要与数据新鲜度匹配**：歌词 / 封面 / 专辑元数据可长缓存（小时~天）；歌单内容中等（分钟）；播放地址最短（其 URL 本身带时效签名）。
- **不要缓存易变状态**：播放状态、一起听房间状态不入缓存，防止状态不一致。

### 6.4 并发控制与优先级调度（「高并发」的正确姿势）

> **反模式警告**：盲目提高并发数会触发网易云风控与 AMLL 限流（官方约 50 次/秒/IP），导致降级甚至封禁，**结果反而更慢**。并发控制的目标是**稳定与可预测，而非最大化并发**。

**统一请求调度器**（`src/net/scheduler.ts`）——按四档优先级排队：

| 优先级 | 任务 | 说明 |
|---|---|---|
| **P0 播放路径** | `/song/url`、当前曲目详情、当前歌词 | 直接决定「切歌到出声」，**永不被低优先级阻塞** |
| **P1 可见区域** | 视口内列表项的详情与封面 | 直接影响首屏观感 |
| **P2 预取** | 下一首的音源/歌词/封面、下一屏列表 | 可延迟，但赶在用户操作之前 |
| **P3 后台补齐** | 非可见区域的元数据批量填充 | **可随时丢弃** |

| 机制 | 说明 |
|---|---|
| 并发上限 | 分目标配置（建议出站至网易云 6–8、AMLL 4–6、本地不限），连续失败时**指数退避** |
| **批量合并（coalescing）** | 把短时间窗口内散落的单曲请求**聚合成批量请求**（`/song/detail?ids=a,b,c…`，单次上限 1000 个 id）。例：歌单页滚动加载 30 首 → 合并为 1 次请求而非 30 次 |
| 可取消队列 | 路由离开时丢弃该页面的 P2/P3 任务，不为已不可见的内容付带宽 |
| 公平性 | 高优先级队列有独立的并发配额，避免后台补齐把播放路径挤到超时 |

### 6.5 预取与预热：把延迟藏进「用户还没点」的时间里

| 手段 | 说明 |
|---|---|
| 已有：下一首音源预取 | `_cacheNextTrack()` 已实现，保留 |
| **扩展：下一首「四件套」并行预取** | 音源 ∥ 歌词 ∥ 封面 ∥ 详情——当前是串行链，改为并行发起 |
| 列表滚动预取 | 滚动到 80% 时预取下一屏数据 |
| 启动预热 | `dns-prefetch` / `preconnect` 到网易云 CDN 与 `api.amll.dev`，提前建立 keep-alive 连接，避免首次请求支付 TLS 握手成本 |
| 兜底重试 | 播放过半时若预取失败，重试一次（网络抖动容错） |

### 6.6 图片加载（数量最多、最易被忽视）

封面图是**请求数量的绝对主力**（列表页每行 1～3 张）。

| 手段 | 说明 |
|---|---|
| 视口懒加载 | 统一 `loading="lazy"` + `IntersectionObserver`（现有代码部分已有，需全面盘点补齐） |
| 尺寸正确 | 列表用 `param=224y224`，仅歌词页/详情大图用 512/1024；**杜绝小图位拉大图** |
| 骨架占位 | 固定宽高比占位，避免加载完成后的布局抖动（CLS） |
| 复用现有预热 | `cacheTrackSource` 已在缓存音频时预请求封面 3 个尺寸（512/224/1024），保留该行为 |
| 可选：本地图片代理 + 磁盘缓存 | 经 `27232` 端口代理并落盘，实现**离线可看**与二次加载零网络；代价是要为缓存目录设计清理策略 |

### 6.7 播放关键路径（切歌到出声）

当前切歌链路是**串行**的：

```
getTrackDetail(id)  →  _getAudioSource(track)  →  Howler(src)  →  出声
       ↑ 网络                  ↑ 可能再等缓存 / 官方 / UNM
```

**改造**：

- **并行化**：详情与音源获取并行（音源只需 `id` 即可请求官方 URL，不强依赖详情）→ 预计省掉 1 个网络往返。
- **缓存优先短路**：IndexedDB 命中时不等任何网络（现有实现已缓存优先，保留）。
- **多源竞速（谨慎）**：仅在「官方 URL 与本地缓存同时可用」时取先到者；**不对多个解锁音源并发竞速**（会放大风控风险）。
- **与调度器联动**：确保 P0 任务与下一首预取不互相挤占。

### 6.8 一起听的轮询成本

双人房轮询节奏：心跳 20s + 播放/歌单同步 4s ≈ **每分钟 15～30 次请求**。服务端 2 分钟缓存在此**帮助有限**（房间状态本就持续变化），需从源头降量：

| 手段 | 说明 |
|---|---|
| **差异上报** | 仅在状态真正变化时上报（`playStatus` 变化、`songId` 变化、进度跳变超阈值），而非定时无条件上报 |
| **自适应心跳** | 静止时拉长间隔（20s → 30s），有播放活动时缩短 |
| **弱网退避** | 连续失败指数退避，避免打爆；恢复后立即补一次全量同步 |
| **房间内不轮询歌词与详情** | 全部走本地缓存，房间只同步「听同一首歌」所需的最小状态 |

### 6.9 验收指标

| 场景 | 目标 |
|---|---|
| 二次打开同一歌单 | **0 次出站请求**（内存/持久缓存全命中） |
| 重复请求率 | **0**（同一 URL 并发冗余请求归零） |
| 切歌到出声（缓存命中） | < 150ms |
| 歌词首次显示（缓存命中 / 远程） | < 300ms / < 1.5s |
| 500 首歌单首屏 | 内容 1s 内可见，图片渐进加载 |
| 搜索响应 | 防抖后 p95 < 600ms |
| 弱网（模拟 3G） | 不出现请求风暴；失败请求有退避且有用户可见反馈 |
| 出站并发峰值 | 不超过配置上限，**无 429 / 风控触发** |

**排期落点**：请求层的**基础部分（去重 / 取消 / 缓存优先修正 / 只读接口禁易变参数）落在 M1**（M1 本就改动 API 层，一起做最省）；**调度器 / 内存 LRU / 批量合并 / 预取并行化落在 M2**（与歌词三级数据源的并发调度天然同源，AMLL 限流也依赖它）。

## 7. 工具链升级方案

| 项 | 现状 | 目标 | 理由 |
|---|---|---|---|
| Node.js | 14 \|\| 16 | **22 LTS** | api-enhanced 要求 22+；现代依赖的硬性前提 |
| 构建 | Webpack 4（vue-cli 4.5） | **Vite 6/7** | 冷启动/构建数量级提升；原生 ESM；**可删除 `esbuild-loader` 降级补丁** |
| 框架 | Vue 2.6.11 | **Vue 2.7** | 内置 Composition API；可接入 `@vitejs/plugin-vue2`；页面/组件零改写 |
| 语言 | JS + JSDoc | **渐进 TS**（新代码 TS，旧文件 `allowJs`） | 歌词引擎需要强类型；允许旧代码不动 |
| Electron | 13.6.7 | **30+ LTS 线** | 安全补丁、现代 API；原生模块需逐项验 ABI |
| 安全模型 | `nodeIntegration:true` + `contextIsolation:false` + `webSecurity:false` | **preload + contextBridge 白名单通道** | 消除 XSS → RCE 路径 |
| 测试 | 无 | **Vitest**（核心逻辑）+ **Playwright**（UI 冒烟） | 播放/歌词解析/一起听防回环必须有回归保护 |
| 格式/检查 | ESLint 6 + Prettier 2.5.1 | **ESLint 9 + Prettier 3**（或 Biome） | 工具链现代化 |
| 包管理 | yarn | **pnpm** | 与 api-enhanced 一致，磁盘效率更高 |
| 原生模块 | `rust-napi` / `mpris-service` / `x11` | 升级后逐项验证 | Electron 大版本升级会改变 ABI |

**升级顺序建议**（降低一次性风险）：

1. Node 22 + pnpm（环境层）
2. Vite 接管构建，**先保持 Vue 2.6**，确认能跑通打包（此时可删 `esbuild-loader`、`LimitChunkCountPlugin` 等 Webpack 遗留）
3. Vue 2.6 → 2.7（近似 drop-in）
4. Electron 13 → 30+，**同步完成 preload/contextBridge 改造**（这两件事必须一起做，否则安全改造要返工两次）
5. 引入 TS（`allowJs` 起步）
6. 补 Vitest 测试

---

> **与安全改造绑定的一个陷阱（必须同批次验证）**：开启 `webSecurity: true` 后，渲染进程**不能再跨源直连** `127.0.0.1:10754`。生产环境本就经 `27232` 同源反代，不受影响；但**开发环境当前正是直连**，会立即失效。二选一：（a）为 api-enhanced 设置 `CORS_ALLOW_ORIGIN=http://localhost:<Vite 端口>`（其 CORS 中间件已支持凭据）；（b）开发环境也统一走 `27232` 反代。详见风险 R11。

**「情绪、风格自主变幻」怎么落地（不引入任何模型）**：情绪档位由调色板自身的
饱和度与明度推断（calm / balanced / energetic），再决定模糊色块的运动周期与强度；
封面是歌曲的情绪名片，静图取色已经把"这首歌什么调性"带进来了，且同一首歌结果可复现。
音频频谱反应按 D12 不在本轮范围。

**从 folia 学到的四个关键取舍**（都写进了组件注释）：

1. **不用 `backdrop-filter`** —— 整屏回读背景，Electron 里每帧代价极高
2. **模糊源先降采样到 384px** —— 40px 模糊看不出更细的细节，而大纹理会分块上传、
   逐块显示（"切歌时网格闪烁"的根因）；384px 是一块纹理，任何封面都不闪
3. **切歌交叉淡入**，且**透明度加在包装层**而不是模糊层 —— 直接给 blur 元素做透明度
   动画会让浏览器每帧重算模糊
4. 色块用 `mix-blend-mode: screen/overlay` 调和，避免多色各说各话

**设置迁移**：`settings.lyricsBackground` 的取值域从 `boolean | 'blur' | 'dynamic'`
扩展为加上 `'fluid'`，**旧值语义完全不变**（升级后行为逐字节一致），因此不需要任何
数据迁移；脏值统一按原有默认 `true` 处理（`normalizeLyricBackgroundStyle`）。

**M3-C 播放交接：不需要做。** 计划书原先假设「透明是建窗期标志 → 切换要重建主窗口 → 播放会断」，

音频自始至终在主窗口里，开/关副窗口不影响播放，因此不需要交接层（少一套 IPC + TTL + 落盘）。

**过程中发现的三处真实缺陷**

1. **副窗口的 `ipcRenderer.on` 回调签名**：preload 的 `on(channel, listener)` 会传入
   占位事件作为第一个参数（`listener({}, ...args)`），新写的监听器按 `payload => …` 取参
   拿到的全是 `{}`。表现是"命令发了没反应、状态永远不更新"，而初始快照拉取又把症状掩盖了。
   已全部改为 `(_event, payload) => …`，并在调用点注释这一约定。
2. **koffi 原生二进制没进产物**：electron-builder 在 pnpm 布局下不带 koffi 的
   optionalDependencies（`@koromix/koffi-<platform>-<arch>`），asar 里只有 JS。
   修法：`beforePack` 钩子按平台暂存到 `build/native/koffi`，再由 `extraResources` 拷到
   `resources/koffi`（koffi 加载器会探测 `resourcesPath/koffi/<triplet>/koffi.node`）。
3. **打包版启动即崩（M1 起就存在，非本次引入）**：`@unblockneteasemusic/rust-napi` 的
   平台包同样没被打包，报 `Cannot find module '@unblockneteasemusic/rust-napi-win32-x64-msvc'`。
   M1 只验证了"打包完成"，没启动过打包产物，所以没暴露 —— 意味着**之前产出的安装包是不可用启动的**。
   修法：把各平台预编译包列为本项目 `optionalDependencies`（pnpm 只装当前平台），
   现在打包产物可正常启动并跑通桌面歌词。

4. **副窗口各自起了播放器（表现为"两个播放源"）**：副窗口为了复用 `LyricLines`
   加载了整个 store，而 `Player._init()` 会从 localStorage 恢复 `_enabled=true` 并
   `_replaceCurrentTrack()` —— 于是桌面歌词窗口、远程控制窗口各加载一路音源
   （系统媒体控制里出现多个会话，静音其中一路另一路还在响）。
   修法：`?win=...` 的窗口**不创建 Player**（播放能力只属于主窗口），
   同时把 `dailyTask()` 也限定在主窗口。实测两个副窗口 `playerIsInstance=false`、
   `howler=false`、`0` 个 audio 元素，歌词仍由 IPC 正常同步。

**打包流程的一个坑（自测记录）**：直接跑 `electron-builder --dir` **不会**重建渲染产物
（`dist/`），会打出旧前端。必须走 `pnpm electron:build:dir`（= `build:electron` + 打包）。
我曾因为跳过了 `build:electron` 而拿到"修好的主进程 + 旧渲染层"的产物，多验证了一轮。

**设置迁移 / 兼容性**：桌面歌词与远程控制都是**新增开关**（默认关闭），不影响任何现有设置；
不支持的系统（非 Windows 11 24H2+）点开关会得到明确提示而不是静默失效。

| 防回环 | 这条 `PLAY` 是**自己**上报的，轮询回来后按账号/签名判定**没有再次应用到本机**（未出现播放被重置） |
| 退出 | 状态清空（inRoom=false、roomId=''、成员 0），服务端房间已结束（再次 create 返回 NEW_ROOM 而非 ALREADY_IN_ROOM），无残留定时器 |
| 错误路径 | 乱输入 → 提示"无法解析分享链接（只支持双人一起听）"；多人房链接被拒；失效房间 → 提示"一起听已失效…"且状态不被污染 |
| **两账号实测后的修正（最终版）** | 成员的上报**会**写入 `sync/playlist/get.playCommand`，但有一个硬性前提：**目标歌曲必须在房间共享歌单里**（详见下节）。成员的操作因此对「官方客户端房主」和「Aki 房主」都可达 |

**两账号实测的完整模型（2026-11-19，多轮实验后定稿）**

早期受控实验用**不存在的歌曲 ID**（987654321）上报，接口返回 200 但房间指令不变，得出了
"成员指令永远进不了房间状态"的错误结论。真人在线房间复测后修正：

1. 成员上报 `PLAY`（目标 `579954`，该歌在房间歌单里）→ `sync/playlist/get` 立刻读到
   `userId=3900179577`、`clientSeq=12` 的指令；
2. 成员上报 `GOTO`（目标 `1489065373`、`604`，**不在**房间歌单里）→ 接口返回
   `{code:200,data:{result:true}}`，但房间指令**完全不变**；
3. 成员调 `sync/list/command/report` 做 `REPLACE`（把上述两首加入歌单）→ 服务端接受，
   歌单版本里出现 `{userId:3900179577, version:999}`，歌单 20 → 22 首。

因此：

| 方向 | 传输 | 是否可用 |
|---|---|---|
| 房主 → 成员（跟随） | `sync/playlist/get` 的 `playCommand` 轮询 | ✅ |
| 成员 → 官方客户端房主 | 同一份房间状态（服务端写入）+ NIM | ✅（目标在歌单内） |
| 成员 → **Aki 房主** | 同一份房间状态 | ✅（目标在歌单内；Aki 房主轮询得到） |
| 成员目标**不在**共享歌单 | — | ❌ 服务端静默丢弃（200 但状态不变） |

**本轮修掉的四个实测问题**

| 症状 | 根因 | 修复 |
|---|---|---|
| 切歌后暂停无法同步、切歌反馈延迟大 | `_remoteSuppressUntil` 原来 20 秒：房主对你的切歌做出反应后上报，你应用时又刷新 20 秒，接下来 20 秒的切歌/暂停全被吞掉 | 缩短为 **1.5 秒**（只盖住应用远端指令本身的回声） |
| 房主切歌本机有时不跟 / 跟随滞后 | `shouldApplyPlayCommand` 用 `clientSeq` 判"自己的回声"，但 clientSeq 是各客户端独立自增的，房主的 1/2/3 与成员发过的撞号，房主指令被误丢 | `sentClientSeqs` 只对**同账号**生效；单测覆盖对方同号 |
| 切歌后播放的音乐不一致 | ① 自动跳歌连发多条 GOTO；② 更关键：目标歌不在共享歌单时服务端静默丢弃，房主停在别的歌上 | GOTO 上报**去抖 500ms**；**切到歌单外先 `REPLACE` 同步歌单再上报**；加入房间时把本机队列对齐共享歌单 |
| 跟随切歌后本地偏离房间 | 跟随场景遇到 VIP/无版权歌自动跳下一首 | 传入 `UNPLAYABLE_CONDITION.STOP`：放不了就停在原地并提示 |

（`UNPLAYABLE_CONDITION` 独立到 `src/utils/playbackConditions.js`，避免 player 与 listenTogether 循环依赖。）

**第三轮实测（真人在线房间）抓到的跟随断点**

`shouldApplyPlayCommand` 原来用 `sentClientSeqs.has(cmd.clientSeq)` 判定"这是自己的回声"，
但 **clientSeq 是每个客户端各自的自增计数器**：房主的 1、2、3… 与成员自己发过的编号必然撞车。
撞上时房主的指令被误判为自己的回声丢弃 → 表现为"房主切歌，本机有时不跟随/跟随滞后"。

修复：`sentClientSeqs` 只对**同账号**的命令生效（`String(cmd.userId) === String(userId)`），
不同账号之间根本不需要比编号。单测补了两条（同账号去重仍生效；对方同号必须应用）。

**最终验收（2026-11-19，用户实机确认）**

| 验收项 | 结果 |
|---|---|
| ① 播放/暂停双向 4 秒内跟随 | ✅ 房间指令 1.3 秒写入；房主操作 → 本机跟随 |
| ② 切歌同步 | ✅ 目标一致（歌单内），1.2 秒写入房间状态 |
| ③ 进度偏差 < 5 秒 | ✅ **用户实机确认**：房主拖动进度后成员自动跟进，偏差保持在 5 秒内 |
| ④ 房间歌单 REPLACE | ✅ 成员 REPLACE 被接受；进房队列自动对齐共享歌单 |
| ⑤ 退出/结束干净 | ✅ 状态清零、服务端房间结束、定时器清理 |
| 断线可恢复 | ✅ **用户实机确认**：网络中断约 20 秒后恢复，未丢房、同步自动继续（非 488 错误只重试） |

至此 §5.4 五项验收全部通过，M4 完成。
