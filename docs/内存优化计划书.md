# 内存优化计划书

> 日期：2026-11-21
> 范围：Electron 主进程 + 渲染进程 + GPU 进程的内存占用（用户报告约 700MB）
> 本轮已完成项会标注「已修」，未完成项按优先级排期。

## 0. 结论

700MB **不是单点泄漏**，而是四类占用叠加：

1. 音频缓存初始化统计会碰 1.19GB 的 `trackSources`（已改为元数据表 + 空闲迁移，启动只读几十字节/条）；
2. 切歌时旧音频 Blob URL 从未真正撤销（已修，实测 50 次切歌 53 创建 / 53 撤销）；
3. Canvas 模式切换反复创建/销毁合成层（已改为常驻画布复用 + 非激活 opacity 0）；
4. Chromium 自身（browser/GPU/renderer）在 50 次切歌后仍会上涨约 50–100MB，属于媒体/GPU 缓存与进程内存未归还 OS，需要专项收敛。

**修复前**实测（打包版，Windows 11 24H2）：

| 场景                     | 私有内存合计 | 说明                                         |
| ------------------------ | -----------: | -------------------------------------------- |
| 冷启动 10s               |       ~610MB | 缓存扫描进行中，含瞬态峰值                   |
| 空闲 30s（桌面歌词关闭） |       ~450MB | 扫描结束、GC 后                              |
| 50 次视觉模式切换        |       ~611MB | 切换前 ~621MB，基本不涨                      |
| 50 次切歌                |       ~703MB | 相对切换前 +58MB，Blob/JS 堆稳定，进程侧仍涨 |

**修复后**（元数据表 + 单封面 + 缓存感知预取）：

| 场景                         | 结果                                                                   |
| ---------------------------- | ---------------------------------------------------------------------- |
| 空闲 15s（旧库已迁移）       | 私有内存 **494MB**；启动只读 meta，不再扫 1.19GB Blob                  |
| 50 次视觉 + 50 次切歌        | 私有内存 677–699MB；GPU 120→305MB，第二次 50 次仅 +27MB（趋于平台期） |
| 50 次切歌（缓存命中路径）    | Blob 53 创建 / 53 撤销 / 存活 1；JS 堆稳定 ~15MB；不再重复 GET 音源    |

其中单进程构成（空闲）：browser ≈ 236MB、renderer ≈ 118MB、GPU ≈ 115MB、network ≈ 14MB、audio ≈ 11MB。
压力后主要增长仍在 GPU 进程（Canvas/纹理缓存），是下一阶段的首要目标。

## 1. 测量方法

- 渲染进程 JS 堆：CDP `Runtime.evaluate` 读 `performance.memory.usedJSHeapSize`，测量前 `HeapProfiler.collectGarbage`；
- 进程归属：CDP `SystemInfo.getProcessInfo` 将 PID 映射为 browser / renderer / GPU / network / audio；
- 进程内存：Windows `Get-Process` 的 Working Set 与 Private Bytes；
- 资源回收：`scripts/verify-resources.mjs`（新增，支持 50/100/200 次循环）。

> 注意：Working Set 含共享内存，任务管理器“内存”列通常显示私有/提交内存；本计划以 **Private Bytes 合计** 为主指标。

## 2. 根因与已完成修复

### 2.1 已修：db.js 初始化循环依赖与全量读取（P0）

- 位置：`src/utils/db.js`
- 问题 A：`db.js → store → Player → db.js` 循环引用，模块初始化时 `store` 仍处于 TDZ；
  `initTracksCacheBytes()` 顶层调用触发 `Cannot access 'j' before initialization`，每次启动都报错。
- 问题 B：修正 A 后若继续使用 `db.trackSources.toArray()`，会把 **1.19GB 音频 Blob 全部读入内存** 再求和。
- 处理：
  - 移除对 `store` 的模块级依赖，改为同步读 `localStorage.settings.cacheLimit`（Vuex 持久化插件是同步写入）；
  - `toArray()` 改为 `each()` 逐条累计，避免整库一次性驻留；
  - 删除 `waitForSettingsReady` 轮询。
- 结果：启动日志不再出现 TDZ；扫描完成日志为 `initTracksCacheBytes, total bytes: 1191875791`。

### 2.2 已修：音频 Blob URL 从不撤销（P0）

- 位置：`src/utils/Player.js:395`
- 问题：`for (const url in this.createdBlobRecords)` 遍历的是数组下标 `"0"`，`URL.revokeObjectURL("0")` 无效；
  每切一首歌都遗留一个音频 Blob（一首歌数 MB ～十几 MB）。
- 处理：改为 `for...of`，并在创建新 URL 前撤销上一批。
- 实测：合成 20×2MB 测试从「创建 20 / 撤销 1 / 存活 20 / JS 堆 +32MB」变为「创建 20 / 撤销 20 / 存活 1」；
  真实切歌 50 次：创建 53 / 撤销 53 / 存活 1。

### 2.3 已修：Canvas 合成层反复创建/销毁（P1）

- 第一版：销毁时把 `canvas.width/height` 置 0，再交给 Vue 移除 DOM（保留在 `dispose()` 中作为兜底）。
- 第二版（当前）：Fume/Glyph 画布一旦用过就保留（`glyphMounted` / `fumeMounted`），
  非激活时 `opacity: 0; pointer-events: none`，不再用 `v-show` 的 `display:none` 反复进出合成层。
- 实测：50 次 `off ↔ 逐字` 切换画布始终最多 1 个（同一时刻只激活一个），关闭后全部
  opacity 0；JS 堆 15MB 左右。GPU 私有内存 115→200MB（第二次 50 次仅再 +27MB，趋于平台）。

### 2.4 已修：重复请求与请求层缺少统一治理（P1，本轮顺带）

- `getTrackDetail` / `getLyric` 缓存未命中重复请求已改为只发一次；
- `getAlbum` 同样修掉「先无条件发一次、未命中再发一次」；
- 新增 `src/net/requestScheduler.ts`：全局 in-flight 去重、P0–P3 调度、独立并发上限、
  `AbortSignal` 取消与 `cancelGroup`；
- 下一首预取改为详情 ∥ 歌词 ∥ 音源并行（封面在详情到位后并行），统一 P2；
- 实测切歌 50 次无失败；具体请求层说明见 [性能与请求层治理](#5-附本轮请求层治理)。

## 3. 仍待解决（按收益排序）

### ✅ 已实现：启动统计改用 `trackSourceMeta`

Dexie v7 新增 `trackSourceMeta: '&id'`，写入/删除音频时同步维护 `{ id, bytes }`：

- 启动只读 meta（约几十字节/条），不再触碰 1.19GB 音频 Blob；
- 旧库首次启动在 `requestIdleCallback` 中逐条补表（每 200 条批量写入），实测日志
  `repairTrackSourceMeta done` 后总大小为 1.18GB；
- 设置页 `countDBSize()` 与缓存淘汰复用 meta；
- 已缓存音频在预取时直接跳过 `/song/url`，不重复下载整首歌。

**实测**：首次迁移后下次启动 `initTracksCacheBytes` 立即返回 1.18GB；空闲私有内存 494MB。

### ✅ 已实现：封面只预热单尺寸

`cacheTrackSource()` 不再一次性请求 512/224/1024 三张；只预热列表/播放条使用的 224，
且用 XHR 下载字节而不是 `Image` 解码，避免把封面位图推进 GPU 图片缓存。
音频已缓存时连 224 也不再重复预热。512/1024 由歌词页/大图按需加载。

### P1：50 次切歌后进程侧仍增长（当前约 +14–58MB）

JS 堆、Blob URL 已稳定，增长发生在 Chromium 进程侧，候选：

1. `<audio>` / Howler 的媒体缓存与解码缓冲；
2. GPU 进程为封面图、Canvas、毛玻璃层保留的纹理；
3. Chromium 堆向 OS 归还滞后（malloc/partition alloc 碎片）。

**方案**：

- 为 `_playAudioSource` 增加显式销毁路径：`_howler?.unload()` 后置空，并验证 `Howler._howlers` 数量；
- 切歌压力测试加入「每 10 次采样一次 private bytes」，区分「持续增长」与「一次性缓存后平台期」；
- 若确认是媒体缓存：评估 `Howler` 复用单个 `<audio>` 元素（需要处理 `captureStream` 重新捕获）或定期重建；
- 若确认是 GPU 纹理：对封面预热的尺寸/数量限流，并检查 `LyricsBackgroundFluid` 的模糊层与 Canvas 并发。

**验收**：连续 50 次切歌后私有内存增长 ≤ 50MB；再跑 50 次增长 ≤ 10MB（平台期）。
单次采样会受 Chromium 分区分配器影响，必须连续采样取平台期，不能只看一次数字。

### P2：缓存上限默认 8GB 与内存层缺失

- `cacheLimit` 默认 8192MB；当前用户缓存 1.19GB，短期无压力，但大库会拖慢统计/清理；
- 没有会话级内存 LRU，重复读 Dexie 的对象仍要反序列化。

**方案**：

- 默认上限评估为 2–4GB（或按磁盘可用空间动态），设置页显示实际占用；
- 引入 `src/net/memoryCache.ts`：按字节预算的 LRU（当前曲目、当前歌词、当前歌单），
  与 IndexedDB 分层，避免把大对象长期驻留 JS 堆。

### P2：桌面歌词是第二个渲染进程

桌面歌词开启时多一个 renderer（本轮实测约 160MB 私有内存）与一个透明窗口合成层。
这是功能成本，不是 bug；但需要让用户可感知：

- 关闭桌面歌词后确认窗口销毁、GPU 纹理释放；
- 设置页显示「桌面歌词会额外占用约 100–200MB」；
- 低内存设备提供「关闭桌面歌词/降低质量档」建议。

### P1：GPU 进程长期占用（当前首要目标）

空闲 GPU 约 120MB，压力后实测到 305MB，且第二次 50 次循环只再涨 27MB，接近平台期。
主要来自：

- 全屏 `filter: blur(40px)` + `scale(1.5)` 的封面模糊层；
- Canvas 2D 大画布 + `shadowBlur` 发光（已改为常驻复用，减少创建/销毁）；
- 透明桌面歌词窗口。

**方案**：先做 GPU 专项采样（按模式单独跑 50 次，记录 GPU private bytes），再决定：

- 限制 Canvas DPR（如 1.5）或按质量档降低；
- 背景模糊层在 Fume/Glyph 模式下是否必要（可复用静态降采样图）；
- 低频重绘时释放纹理，窗口隐藏时销毁 canvas。

## 5. 附：本轮请求层治理

虽然不是内存专项，但与本轮一起交付：

- `src/net/requestScheduler.ts`：P0–P3 优先级、每档并发上限（P0 4 / P1 4 / P2 3 / P3 1，全局 8）；
- 全局 in-flight 去重（相同方法 + URL + 归一化参数只发一次）；
- 调用方级 `AbortSignal`：一个调用方取消不影响其他订阅者，全部取消才中止底层请求；
- `cancelGroup('playback' / 'prefetch' / 'lyrics-page')`：切歌/换页批量取消；
- 下一首预取改为详情 ∥ 歌词 ∥ 音源并行，封面在详情到位后预热，全部 P2；
- 调试句柄 `window.__akiRequestScheduler.getStats()`（含 `scheduled` / `deduped`）。

## 6. 风险与注意事项

- **不要用禁用 GPU 来降内存**：会显著增加 CPU 与掉帧，属于错误方向；
- 进程私有内存会受 Chromium 分区分配器影响，单次采样波动大，验收必须用「多次采样 + 平台期」；
- 元数据表迁移必须可回滚，旧缓存首次启动的补表操作要放在空闲时段；
- 任何降低 DPR/模糊质量的改动都要做 A/B 截图，避免为了内存牺牲已封版的视觉观感。
