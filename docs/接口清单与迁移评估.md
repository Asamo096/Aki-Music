# 接口清单与 api-enhanced 迁移评估

> 目的：在决定是否把内嵌 API 包从 `@neteaseapireborn/api@4.29.7` 迁移到
> `@neteasecloudmusicapienhanced/api@4.41.1`（api-enhanced）之前，先查清
> **①接口有没有缺口 ②用的是不是废弃接口 ③迁移到底值不值**。
>
> 结论：**接口没有缺口，迁移不是补功能，而只是换一个还在维护的实现。**
> 评估日期：2026-10-11 · 评估对象：`src/ncmModDef.js` 注册的 124 个模块

---

## TL;DR

| 问题 | 结论 |
|---|---|
| 有没有接口缺失？ | **没有**。124 个注册模块在 api-enhanced 中全部存在，底层请求路径 **0 处差异**，参数仅 2 处为 enhanced 新增的**可选**参数 |
| 前端实际用了多少？ | **58 个**（其余 66 个是上游"接口白名单尽量全"留下的死重） |
| 用了废弃接口吗？ | **1 个**：`/top/list`（api-enhanced 文档中划删除线）——但**前端并未调用**；另有 1 个已被项目自行绕过（`/scrobble`） |
| 路线图（逐字歌词／一起听）需要新接口吗？ | **不需要新增依赖**。`lyric_new` 与 9 个 `listentogether_*` 在当前包里已有，且与 enhanced **逐字节相同**（仅行尾差异） |
| 迁移值得吗？ | 功能上**零收益**；理由是维护性——当前包在 npm 上已标记 *Package no longer supported* |

## 一、迁移可行性：逐项比对

| 比对维度 | 结果 |
|---|---|
| 模块存在性 | **124 / 124 全部存在**（api-enhanced 共 449 个模块，是当前包 362 个的超集） |
| 底层请求路径 | **0 处差异**（含多 `request()` 分支的模块） |
| 参数键（`query.*`） | **2 处差异，均为 enhanced 新增可选参数**：`recommend_songs.afresh`、`login_cellphone.sca`（secureCaptcha） |
| 登录参数兼容性 | **向后兼容**。`login.js`: `password: query.md5_password \|\| MD5(query.password)`；`login_cellphone.js` 同理，并支持 `captcha` 分支 |
| 自定义模块 | 1 个：本项目在 `ncmModDef` 中注册的本地 `/scrobble`（`src/electron/scrobble.js`），与 API 包无关，迁移时保留 |

> 比对方法：解析 `ncmModDef.js` 的 `identifier/route/module` 三元组，
> 对每个模块提取两个包中的全部 `request('<path>')` 目标与 `query.*` 键集合做差集。

**结论：迁移是纯机械替换（124 行 require 路径），不存在功能缺口。**

## 三、注册但未使用的接口（66 个）

上游 `ncmModDef` 按"接口尽量全"的口径注册了 124 个，**前端实际只调用 58 个**。

**未使用清单**（按类别）：

- **user（11）**：`/user/update` `/user/subcount` `/user/replacephone` `/user/level` `/user/follows` `/user/followeds` `/user/event` `/user/dj` `/user/bindingcellphone` `/user/binding` `/user/audio`
- **playlist（17）**：`/playlist/update` `/playlist/track/delete` `/playlist/track/add` `/playlist/track/all` `/playlist/tags/update` `/playlist/subscribers` `/playlist/privacy` `/playlist/order/update` `/playlist/name/update` `/playlist/mylike` `/playlist/hot` `/playlist/highquality/tags` `/playlist/detail/dynamic` `/playlist/desc/update` `/playlist/cover/update` `/playlist/video/recent`
- **artist / album（17）**：`/artist/video` `/artist/top/song` `/artist/songs` `/artist/new/song` `/artist/new/mv` `/artist/list` `/artist/fans` `/artist/detail` `/artist/desc` `/album/songsaleboard` `/album/newest` `/album/list/style` `/album/list` `/album/detail` 等
- **mv / topic / 其它（21）**：`/mv/first` `/mv/exclusive/rcmd` `/mv/detail/info` `/mv/all` `/top/mv` `/top/list` `/top/artists` `/top/album` `/topic/*` `/login/status` `/follow` `/cloudsearch` `/check/music` `/cellphone/existence/check` `/captcha/verify` `/captcha/sent` `/calendar` `/batch` `/banner` `/avatar/upload` `/audio/match` `/activate/init/profile` `/song/download/url`

**两点说明**：

1. **有些"未使用"是因为应用改用了更合并的接口**，不是功能缺失。例：
   - 歌单增删曲目用 `/playlist/tracks`（批量合并接口），而不是 `/playlist/track/add`、`/playlist/track/delete`
   - 歌手页用 `/artists`（一次返回简介 + 热门歌曲），而不是 `/artist/songs`
   - 首页**不使用** `/banner` 接口（源码中不出现）
2. **摘除死重是可选优化**：它是一份显式白名单，删掉能略微缩小攻击面，但没有任何功能影响。
   建议**在 M2 动 `ncmModDef` 时顺手整理**，而不是单独做一次改动。

## 四、有更新版、但我们用着旧版的接口（8 组，均非破坏性）

api-enhanced 为若干接口提供了 `_v1` / `_new` / `_v2` 变体。差别通常不在功能，而在
**加密方式（weapi → xeapi）与端点路径**：

| 我们在用 | 路径 | 更新版 | 差异 |
|---|---|---|---|
| `song_url` | `/api/song/enhance/player/url` | `song_url_v1` | 旧版用 `br`（码率）选音质；v1 改用 `level`（standard/exhigh/lossless/hires/jymaster/sky）并换用 **xeapi** |
| `song_download_url` | `/api/song/enhance/download/url` | `song_download_url_v1` | 同族 |
| `lyric` | `/api/song/lyric` | `lyric_new` | v1 额外返回 **yrc（逐字歌词）** → M2 需要 |
| `recommend_songs` | `/api/v3/discovery/recommend/songs` | `recommend_songs_v1` | 路径相同，仅加密 weapi → **xeapi** |
| `like` | `/api/radio/like` | `like_v1` | 路径 → `/api/v1/radio/like` |
| `captcha_sent` | `/api/sms/captcha/sent` | `captcha_sent_v1` | 路径 → `/api/middle/captcha/sent/v1` |
| `user_detail` | `/api/v1/user/detail/:uid` | `user_detail_new` | 路径 → `/api/w/v1/user/detail/:uid` |
| `toplist_detail` | `/api/toplist/detail` | `toplist_detail_v2` | 路径 → `/api/toplist/detail/v2` |

> ⚠ 排查时出现过一处**假阳性**：`album` 与 `album_new` 名字相近但功能完全不同
> （专辑详情 vs 新碟上架），不是新旧关系。

## 六、建议

### 推荐：不整体迁移，按需补注册

理由：

1. **功能上零收益**——124 个模块的请求路径与参数完全一致；M2/M4 需要的模块当前包已有，且实现与 enhanced 相同。
2. **省一次 124 模块的回归验证**——迁移后要逐个确认 58 个在用接口，而收益只是"换实现"。
3. `ncmModDef` 只在需要新增接口时才动，**避免为同一文件做两次改动**。

具体做法：

| 时机 | 动作 |
|---|---|
| M2 做逐字歌词时 | 在 `ncmModDef` 加一条 `lyric_new` 注册（当前包即可），同时**顺手摘除 66 个死重中的 `user_*` / `playlist_*` 等无用项** |
| M4 做一起听时 | 加 9 条 `listentogether_*` 注册（当前包即可） |
| 若要做音质升级 / 内置解灰 | 这是**唯一需要额外决策**的点：<br>① 装 `@unblockneteasemusic/server`（JS 版 UNM，与现有 `rust-napi` 重复，约多一份音源实现）<br>② 或此时顺便迁到 api-enhanced（其 `song_url_v1` 用 `unblockmusic-utils` + xeapi） |

### 若决定迁移，成本与风险

- **改动**：`ncmModDef.js` 中 124 行 `require` 路径（`@neteaseapireborn/api/module/x` → `@neteasecloudmusicapienhanced/api/module/x`）+ `package.json` 依赖替换
- **验证范围**：只需回归**前端实际使用的 58 个接口**（清单见 `src/api/*.js` 的 `url:` 字段）
- **风险**：低（路径与参数一致），但需注意 enhanced 的部分模块行为更"新"（xeapi、部分模块带 `unblock` 参数），需确认不会改变现有调用语义
- **唯一实质理由**：当前包在 npm 上已标记 *Package no longer supported*，不再有修复；若网易调整风控导致 weapi 失效，旧包不会跟进

## 附录 A：注册路由的顺序约束（重要，加新路由前必读）

`ncmModDef.js` 注册的路由**不是精确匹配，而是前缀匹配**——API 服务用
`app.use(route, handler)` 注册（见 `@neteaseapireborn/api/lib` 的 `server.js`）。
因此**短路径会吞掉长路径**：

| 顺序 | 结果 |
|---|---|
| `/lyric` **在** `/lyric/new` 之前 | ✗ `/lyric/new` 被 `/lyric` 接管：返回老接口内容（lrc 1436 字符、**无 yrc**） |
| `/lyric/new` **在** `/lyric` 之前 | ✓ 各走各的 |

这正是本文件里 `/album` 排在一堆 `/album/xxx` **之后**、`/api` 排在**最后**的原因——
顺序是刻意安排的，不是随手写的。

**自查脚本**（新增路由后跑一次，当前 125 条无冲突）：

```bash
node --input-type=module -e "
import fs from 'node:fs';
const s = fs.readFileSync('src/ncmModDef.js','utf8');
const routes = [...s.matchAll(/route:\s*'([^']+)'/g)].map(m=>m[1]);
for (let i=0;i<routes.length;i++)
  for (let j=0;j<i;j++)
    if (routes[i].startsWith(routes[j]+'/')) console.log('✗ 被遮蔽:', routes[i], '←', routes[j]);
console.log('扫描完成，共', routes.length, '条');
"
```

## 附录 B：`/lyric/new` 已注册并验证（2026-10-11）

`/lyric/new` 已加入 `ncmModDef`（排在 `/lyric` 之前），并**实测拿到逐字歌词**。

**响应字段**（对比老接口）：

| 字段 | `/lyric`（老） | `/lyric/new`（新） |
|---|---|---|
| `lrc` | 1436 字符 | **2093 字符**（内容更全） |
| `yrc` | 无 | **7311 字符（逐字）** |
| `ytlrc` | 无 | 612 字符（逐字翻译，行级 LRC 格式） |
| `yromalrc` | 无 | 1458 字符（逐字罗马音） |

> 同一首歌（示例 id `1824020871`）的实测值。注意**老接口的 lrc 与逐字接口的 lrc 内容不同**，
> 迁移时不能假设两者等价。

**`yrc` 数据格式**（M2 解析器需要）：

```
[20570,1900](20570,360,0)初(20930,150,0)め(21080,120,0)て…
 ~~~~1 ~~~2  ~~~~3 ~~4 5 ~6
```

- 每行格式：`[行起始ms,行时长ms](词起始ms,词时长ms,0)词…`
- 行首可能另有若干 **JSON 元数据行**（作曲/编曲/制作人，含艺术家头像与 app 内跳转链接），
  形如 `{"t":0,"c":[{"tx":"作曲: "},{"tx":"柳重言","li":"…","or":"orpheus://…"}]}`，解析时需先跳过
- 实测样本：50 行 = 4 行元数据 + 45 行逐字歌词；单行可含 11 个词/音节
